Menu & triggers

A menu is two parts: a trigger you press and a pane that floats open. The DS ships both: the pane (.menu) and the trigger family (.menu-btn, graduated v2.1.3). Neither is hand-rolled any more — this page was still describing the pre-v2.1.3 state, corrected 2026-07-30.

1 · The pane — .menu (menu.css). Ships today. This is what every trigger opens.

Multi-select mode — a real <input type="checkbox"> in front of each row. For set-valued fields whose options have no mark to draw (company names, cohort slugs, role names); anything with an icon takes .grants in forms.css instead.

One component, two modes, and the difference carries meaning: --on tints the ONE current value; a checkbox marks each of MANY and takes no tint — tinting every checked row turns the menu into a block of colour and stops the tint meaning "this one". The menu stays open on pick; the trigger carries the summary.

Slots: .menu__item (button or link) · --on current choice (accent tint) · --danger destructive · .menu__sep divider. Disclosure pattern: trigger toggles .is-open, outside-click / Esc closes.

1b · Theme row — .menu__theme + .seg--fill.seg--icon. Graduated 2026-07-30 from the dark mock. This block is the copy source — the DS ships no icon file, so the three glyphs live in markup like every other icon in v2.

Why the user menu and not a settings page. Dark is an account preference, and putting the control here is what makes the light-only rule for outward-facing pages enforce itself: a respondent opening a token link has no user, so no menu, so no way to turn dark on (PRODUCT.md rule 2). No “ธีม” caption — caption-zero; three glyphs already say it. Every option carries an aria-label, because a glyph button has no accessible name otherwise. Icons stay in markup. v2 ships no icon sprite and this is not the moment to invent one — .menu__item, .shell__item and .toast__close all draw inline too. Copy the three above; they are the house stroke (1.6, round caps).

The DS supplies no JavaScript — theming is one attribute, and persistence is the app's. The whole contract is: document.documentElement.dataset.theme = mode, remember mode against the signed-in user, and stamp it before first paint so the page does not flash. Note “system” needs no listener: CSS reads prefers-color-scheme itself, so an OS flip at dusk repaints a page that is already open.

2 · Triggers — .menu-btn family (menu.css). Ships today, graduated v2.1.3. Body-size type, line-height:normal — a trigger is a control, not a caption. (Said 1 until 2026-07-30; menu.css uses normal, which lands the ink dead centre where 1 sits 0.5px high.)

a · Select-trigger — pick one value
b · Kebab — row / card actions

One face, two shapes. Both are a white .menu-btn (card fill, rule border, r-base) that opens .menu — --kebab is just icon-only. The app-switcher & user menu keep their bespoke triggers in shell.css (shell-specific), not this family.

3 · Why this page exists

The pane was a DS component with no gallery, so it was invisible and got re-implemented (.rmenu) instead of reused. And "button that opens a menu" was never a DS component at all — it lived as .statusbtn, .rchip, the kebab, the app-switcher, the user menu: five copies, zero source of truth. Approve .menu-btn + --kebab and they graduate into menu.css, then .statusbtn and cowork's .rchip retrofit to it — one atomic change.
